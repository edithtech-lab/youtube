# PRD — 원본 고정 + 버전 파일명 (A안)

> 작성 2026-08-19 · 상태: **구현·검증 완료** (실전: 판수 2 → 재생성 1 = v1·v2·v3, v1 md5 불변)
> 확정 사양(2차 검토 반영): 전 판 동등 `_v1`부터 · 앱 표시는 **최신 판** + 버전 칩 전환 ·
> 파일은 절대 이동/덮어쓰기 없음 · **영상만** 적용(이미지는 현행 v폴더 유지 — 앱이
> 이미지 경로를 실제로 읽기 때문) · 자료 소스 탭 포함 · [교체] 버튼은 2단계.
> 배경: 캡컷에서 편집 중인 소재가 재생성 한 번에 조용히 다른 영상으로 바뀌는 문제.

## 1. 문제

지금은 **메인 폴더의 파일명이 고정**이고 재생성 때 옛 파일이 `v1/` 로 밀려난다.
즉 같은 이름의 자리에 **다른 내용**이 들어온다.

캡컷은 소재를 **경로+파일명**으로 물고 있다 → 편집 중 재생성하면 타임라인의 그림이
예고 없이 바뀐다. 컷 길이·타이밍은 그대로라 어긋난 걸 나중에야 발견한다.

## 2. 목표

- **G1** 한 번 만든 파일은 앱이 절대 덮거나 옮기지 않는다 (캡컷이 문 소재 불변)
- **G2** 새로 뽑은 판은 같은 폴더에 **이름으로 구분**해 쌓인다 (내림차순 정렬로 최신 확인)
- **G3** 앱 내부 동작(체인·시작 프레임·미리보기·컷 카드)은 흔들리지 않는다
- **비목표**: 자동으로 "좋은 판" 고르기, 캡컷 프로젝트 직접 수정

## 3. 규칙 (핵심 — 확정본)

```
01_현관 바닥 폼 신발_v1.mp4     ← 1판째. 전 판이 동등하다 (특별한 '원본'을 두지 않는다)
01_현관 바닥 폼 신발_v2.mp4     ← 다음 판
01_현관 바닥 폼 신발_v3.mp4
_미리보기/01_현관 바닥 폼 신발_v2.webm   ← 짝은 같은 이름 규칙
```

- **R1 파일 불변**: 이미 만든 파일은 앱이 **옮기지도 덮지도 않는다.**
- **R2 판 누적**: 재생성은 폴더를 보고 **비어 있는 다음 번호**로 저장한다
  (앱 재시작·다른 세션과 무관하게 이어진다).
- **R3 앱 표시는 최신 판**: 컷 카드는 방금 만든 판을 보여주고, 📼 칩으로 다른 판을
  볼 수 있다. 칩은 **보기 전환일 뿐** — 저장되는 '대표 판' 상태를 만들지 않는다.
  체인(from_prev)도 최신 판을 이어 표시와 일치시킨다.
- **R4 교체는 사람이**: 캡컷에 넣을 판은 사용자가 파일로 고른다. 앱 안 [이 판으로 교체]
  버튼은 2단계 (캡컷이 물고 있는 파일을 바꾸는 행위라 상황을 아는 사람이 해야 한다).
- **R5 적용 범위**: 영상(컷 영상 + 자료 소스). **이미지는 현행 v폴더 유지** — 앱이
  이미지 경로를 실제로 읽기 때문(시작·도착 프레임, 조립 CLEAN 짝, 컷 카드).

## 4. 판수(passes)와의 상호작용 — 확인된 리스크

현재 판수 N 은 **같은 배치를 N번 반복**하며 컷마다 이전 결과를 v 폴더로 민다.
A안에서는 이렇게 된다:

| 상황 | 결과 |
|---|---|
| 첫 배치, 판수 1 | `01_장면.mp4` (원본) |
| 첫 배치, **판수 3** | `01_장면.mp4` + `_v2` + `_v3` — 한 번에 3개 |
| 다음날 재생성 판수 2 | `_v4` + `_v5` 로 이어 쌓임 |

- **R6 판수는 그대로 동작한다** — 판마다 다음 빈 번호로 저장될 뿐이다.
- ⚠ **리스크 A**: 판수 3 × 14컷 = 42개 mp4 + 42개 webm 이 한 폴더에.
  → 대책: 파일명이 `NN_장면_vN` 이라 **이름 정렬만으로 컷별·판별로 모인다.**
    (v 폴더 방식은 폴더를 오가야 비교됐다 — 오히려 개선)
- ⚠ **리스크 B**: 첫 배치가 판수 3이면 **원본이 1판째로 굳는다**(2·3판이 더 좋아도).
  → 대책: R4 수동 승격. 또는 "첫 배치는 판수 1로 뽑고, 마음에 안 들면 재생성"이 자연스러운 흐름.
- ⚠ **리스크 C**: 디스크. 6초 720p 클립 ≈ 3~6MB → 판수 3, 14컷 ≈ 200MB/편.
  → 대책: 편 끝나면 `_v*` 일괄 삭제 (이름 패턴이라 정렬·선택이 쉽다).

## 4-b. 2차 검토에서 찾은 리스크 (구현에 반영)

| # | 리스크 | 대책 |
|---|---|---|
| ① | 문자열 정렬이면 `_v10 < _v2` — 판 10개 넘으면 최신 판정이 조용히 틀림 | 숫자를 뽑아 **정수 정렬**(natural sort) |
| ② | 재생성 사이에 장면 요약을 고치면 같은 컷의 판이 다른 이름 계열로 흩어짐 | 버전 스캔·칩 묶음은 **컷 번호(`NN_`) 기준** |
| ③ | 옛 편 폴더의 구규칙 파일(`01_장면.mp4`, 번호 없음)과 혼합 | 번호 없는 파일 = **v0(레거시)** 로 최신 판정에 포함 |
| ④ | 생성 실패로 남은 반쪽 파일이 '최신 판'으로 잡힘 | 실패 시 **새 파일 즉시 삭제** |

## 5. 앱 내부 영향 지점 (구현 완료)

- `vid_versions` / `vid_latest` / `vid_next_path` 신설 (모듈 함수)
- 영상 저장 경로 → `vid_next_path`, `_archive_prev` 영상 호출 제거
- 실패 시 → 반쪽 파일 삭제 (되돌릴 원본이 없어 로직이 더 단순해졌다)
- `_resolve_prev_clip` → 최신 판 반환
- `_make_preview` → 같은 이름 규칙이라 짝 자동 유지
- 컷 카드 → 최신 판 표시 + 📼 칩 · `vid_vers` API
- `_영상프롬프트.json` → 컷 번호 기준이라 영향 없음

## 6. 성공 기준

1. 편집 중인 `01_장면.mp4` 가 재생성 후에도 **바이트 단위로 동일**
2. 재생성 결과가 `_v2`, `_v3` 으로 쌓이고 미리보기 짝이 맞음
3. 체인 컷이 원본을 이어 붙임 (후보를 물지 않음)
4. 판수 3 배치가 정상 완주하고 파일이 42개 생성됨
5. 회귀 검사 전 항목 통과

## 7. 확정된 결정

- 적용 범위 — **영상만** (이미지는 현행 유지)
- 표기 — **`_v1`부터**, 전 판 동등
- [이 판으로 교체] 버튼 — **2단계로 미룸** (지금은 탐색기에서 파일로)

## 8. 구현 결과 (2026-08-19)

- `vid_versions/vid_latest/vid_next_path` 신설 — 폴더의 실제 파일을 보고 판을 정한다
- 영상 저장 경로가 `NN_장면_vN.mp4` 로 전환, `_archive_prev` 영상 호출 제거
- 실패 시 반쪽 파일 삭제 · `_resolve_prev_clip` 은 최신 판 · 자료 소스 탭 동일 규칙
- 컷 카드에 📼 판 칩 (보기 전환 전용, 저장 상태 없음) · `vid_vers` API
- **이미지는 현행 유지** — 앱이 이미지 경로를 실제로 읽기 때문 (체인·조립 CLEAN 짝 등)

검증: 단위 4건(정수 정렬·컷번호 묶음·레거시 v0·다음 번호) + 실전(판 3개·v1 md5 불변·
미리보기 짝·v폴더 없음) + 회귀 전 항목 통과.
