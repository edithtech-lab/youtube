# 컷 분해 지침 — 2차 검수 회신 (코드 대조 + 실제 산출물 검증)

작성 2026-08-14 · 대상: 1차 진단서(외부 검수 요청서 2026-08-14)에 대한 회신
검증 방법: `main.py`(8,008줄) · `ui/index.html` 코드 직접 대조 + 실제 분해 산출물 1편(「걸어간 모아이」 17컷) 전수 대입

> **이 문서를 읽는 AI에게** — 1차 진단서의 판정을 뒤집는 항목이 있습니다.
> 4장(신규 발견)은 1차 진단서에 없던 내용이며, 그중 4-1은 지침 내부의 자기모순입니다.
> 반박·보완 환영합니다. 다만 **"앱 로직 수정 전제"는 범위 밖**이라는 원 제약은 유지하되,
> 3-0(코드 버그)만은 예외로 보고합니다 — 이걸 안 고치면 지침 항목 일부가 무효이기 때문입니다.

## 1. 시스템 요약 (변경 없음)

```
나레이션 대본(한글)
    ↓  ← 검수 대상 지침 (main.py:2822-3267, 약 450줄)
컷 분해 JSON (컷 15~25개 × 필드 25개)
    ↓  앱이 필드를 이름으로 하나씩 골라 조립
컷별 영어 이미지 프롬프트 (~3,500자)
    ↓  2K 이미지 생성 → I2V 720p 영상 → 편집
```

**설계 원칙:** LLM은 완성된 영어 프롬프트를 쓰지 않는다. 질감·색·카메라·강조 문법은 앱이 갖고,
LLM은 `subject_en`·`style`·`anno_kind`·`motion_en` 같은 **부품 값**만 채운다.

**현재 실행 경로:** `split_input=paste` (claude.ai 웹 → JSON → 사람이 눈으로 보고 앱에 붙여넣기),
`split_model=opus` (API 직행 경로도 있으나 미사용), `anno_max_cuts=4`, `typecast_tempo=1.2`.

**확인된 구조적 사실 (코드 근거):**

| 사실 | 근거 |
|---|---|
| 붙여넣기·API가 **같은 지침 원문**을 씀 (한쪽만 고쳐지는 사고 방지) | `split_guide` 가 `SCENE_SPLIT_PROMPT` 를 슬라이스 (6009-6014) |
| 붙여넣기·API가 **같은 정규화 함수**를 탐 | 둘 다 `_finish_split` (6116) |
| 대본은 통째로 한 번에 들어감 (청크 없음) | `script[:12000]` (6079) — 단 붙여넣기 모드에선 대본이 API로 안 가므로 무의미 |
| 앱이 모르는 필드는 프롬프트를 오염시키지 않음 | `_build_prompt`(6405)가 필드를 이름으로 선택. 최상위는 `title`/`product_hint`/`cuts`만 읽음 |
| **붙여넣기 경로에 대사 전량 커버 검사가 없음** | `_split_script` 의 paste 분기가 `script` 를 아예 참조하지 않음 (6046-6057) |

**추론 속도 상수:** `cps = 8.7 × tempo(1.2) = 10.44자/초` → 컷당 글자 수 **41~83자**(4~8초).
영상 모델이 받는 클립 길이는 4·6·8초 셋뿐이고 **올림** 배정된다(`_assign_cut_secs`).

## 2. 1차 진단 4건에 대한 판정

### 문제 ① "캐논이 확정 전에 컷1을 써버려 표류한다" → **반박. 전제가 틀림**

실제 산출물에서 캐논 문구

> `a colossal Rapa Nui moai statue carved from coarse grey-brown volcanic tuff, elongated head with a heavy straight brow ridge, long narrow nose, thin pressed lips, arms carved flat against the sides with slender fingers meeting over a protruding rounded belly, no legs, deeply pitted weathered stone surface`

가 **컷 1·2·5·7·9·11·12·15 여덟 곳에 토씨 하나 안 틀리고** 들어갔다. 컷 1부터 이미 확정형이었고
컷 15까지 유지됐다. 안 쓴 컷(13 분할화면 / 16 항공 군상 / 17 실루엣 열)은 안 쓰는 게 맞는 자리다.

→ "LLM은 순차 생성이라 캐논을 미리 확정 못 한다"는 메커니즘은 **추론 모델에서 성립하지 않는다.**
계획은 사고 과정에서 서고 출력은 결과를 옮길 뿐이다. 사내 기록 "Opus만 캐논 준수가 좋았다"는
이 진단의 근거가 아니라 **반례**다.

**다만 참인 변형이 셋 있다:**
1. 계획이 출력에 안 남아 **사람이 검증할 수 없다** (= 문제 ④와 같은 문제)
2. **폴백 경로가 Gemini**다(6100, Opus 실패 시 자동 전환). 지침을 Opus 기준으로만 평가하면 안 된다
3. 코드에 캐논 검사는 **없다**. `split_paste` 주석은 "정규화(강조 게이팅·캐논·컷 길이)"라고 적혀
   있으나 `_finish_split` 에 캐논 관련 코드는 한 줄도 없다 — **주석이 사실과 다름**

→ `plan` 블록은 넣을 만하나 **명분을 "캐논 표류 방지" → "검수 가능성 + 폴백 내성"으로 교체**해야 한다.

### 문제 ② "예산이 앞에서 소진되고 뒤가 조용히 꺼진다" → **확인. 산출물이 근접 사고**

`focus_en` 을 채운 컷 = **2, 5, 8, 13 — 정확히 4개**(`anno_max_cuts=4`). 게이팅 통과 여부:

- 컷 2 (beat=hook) → `ANNO_SKIP_BEATS` 이지만 `measure_en="70t"` 예외로 생존 (2549-2557)
- 컷 5·8·13 (constraint/solution/solution) → `ANNO_AUTO_BEATS` 통과
- 합 4 = 상한 → `cap_anno_cuts` 미발동

**한 컷만 더 켰다면** `_rank = (measure 있음 0 / 설명비트 1 / 나머지 2, 동급이면 no 오름차순)` 이므로
**rank 1 중 no 최대인 컷 13(versus, 영상 전체의 회수 컷)이 꺼졌다.** 진단 그대로다.

**지침이 말하지 않는 의존 관계 1건 추가 발견:**
훅 컷은 `measure_en` 이 있거나 `anno_kind=glow` 일 때만 강조가 살아난다. 컷 2가 `scale` 인데
살아난 건 `70t` 덕분이지 도구 덕분이 아니다. [4-a]에 "예외: 훅에서 숫자가 결정적일 때"가
반쯤 적혀 있으나 **의존 관계로는 안 적혀 있다.**

### 문제 ③ "복선·셋업 지시가 없다" → **부분 반박. 더 나쁜 문제가 따로 있음**

Opus는 시키지 않아도 한다. 컷 4에서 통나무 굴리기 통념을 세우고 컷 13 versus 상단 칸에서 회수한다.

**진짜 문제는 그 통념을 두 번 기각한다는 것이다:**
- 컷 4 — 통나무 홀로그램이 **부서져 소멸** (기각 완료)
- 컷 13 — versus 로 **다시 뒤집음** (같은 통념, 두 번째 기각)

컷 13에 도달했을 때 시청자는 9컷 전에 이미 답을 들었다. 회수가 아니라 반복이다.
**"복선을 깔아라"만 추가하면 이 실패는 안 잡히고 오히려 조장된다.**

필요한 문안은 방향이 다르다:
> 한 통념은 **한 번만 기각한다.** 앞 컷에서는 통념을 **세우기만** 하고, 무너뜨리는 건 뒤의 한 컷에서만.
> 홀로그램 기각([3-1]③)과 `versus`([4-d])를 **같은 통념에 둘 다 쓰지 마라** — 뒤에 오는 것이 죽는다.

### 문제 ④ "사람이 JSON을 검수할 수단이 없다" → **확인. 단 사실 D의 진단이 부정확**

`_safe_name(s, n=12)` (3951) — **앞 12자만 남는다.** 실제 산출 파일명:

```
01_새벽 해안 제단 위에 홀.png      ← "홀"에서 잘림
11_해안 제단 도착. 둥근 밑.png
12_같은 제단, 카메라가 상을.png
```

즉 "길게 쓰면 파일명이 깨진다"가 아니라 **"앞 12자가 죄다 수식어라 컷 구분이 안 된다"**이다.

**한글로 사람이 읽을 수 있는 것의 전수 목록:**

| 필드 | 한글? | 프롬프트 도달 | 실사용처 |
|---|---|---|---|
| `line` | ○ | ✕ (자막·타이밍 정렬용) | 낭독·자막 |
| `scene_ko` | ○ | **`subject_en` 이 빌 때만** 폴백 (6409 / T2V 6963) | **파일명 앞 12자**, UI 카드 제목 |
| `search_ko` | ○ | ✕ | 실물 검색어 |
| 나머지 22개 | ✕ | ○ | 영어 자유서술 또는 enum |

→ **이미지를 실제로 결정하는 값 중 한글은 0개.** 붙여넣기 전에 JSON을 봐도 어느 영어 필드가
틀렸는지 알 수 없다는 진단은 정확하다.

## 3. 코드 결함 — 지침 논의의 전제를 바꾸는 1건

### 3-0. `from_en`·`to_en`·`compare_en`·`flow_of` 가 이미지 생성까지 도달하지 못함

```js
// ui/index.html:2747  icPayload — 이미지 생성으로 보내는 필드 전체
{no, scene_ko, subject_en, place_en, shot, type, mode, style,
 beat, focus_en, measure_en, anno, weather_en, chars, anno_kind, anno_label,
 reveal, evidence}
//  ← from_en · to_en · compare_en · flow_of 없음
// ui/index.html:3201  vidPayload 도 동일하게 없음
```

`_finish_split`(6163-6174)은 이 네 필드를 정규화해 `renderCuts`로 내려보내고 `_icCuts`에도
남아 있으나, 생성 요청 시 `icPayload`가 걸러낸다.

**소비처 추적 결과:** `from_en`/`to_en`은 앱 전체에서 `annotation_block`(2422) **한 곳에서만** 쓰인다.
영상 프롬프트 경로는 원래 참조하지 않는다. → **현재 이 두 필드는 앱 어디에도 영향을 주지 않는다.**

**실제 산출물에 대입한 피해:**

| 컷 | 지침 의도 | 실제 화면 |
|---|---|---|
| 2 | scale — 옆에 아파트 3층 홀로 + `70t` 새김 | `compare_en` 누락 → `annotation_block` **`return ""`**. 주석 블록 통째로 없음. **훅의 숫자가 사라짐** |
| 8 | arrow — 배 → 밑동 앞날 끝점 | 화살표는 그려지나 `ANNOTATION_SPAN` 누락, **축은 모델 재량** |
| 13 | versus — 상하 분할 + `MYTH / REALITY` | 분할은 **생존**(Opus가 `subject_en`에도 써넣음), **라벨은 소실** |

컷 13이 반쯤 살아 있는 이유가 중요하다 — **모델이 지침이 시키지 않은 이중 기입을 했기 때문**이고,
그래서 이 버그가 여태 드러나지 않았다.

**테스트로도 안 잡힌다:** `tests/e2e_anno.py:34` 의 `ic_payload` 가 프론트 payload를 복사해둔
물건이라 같은 필드를 빠뜨린 채 검증한다.

**조치:** `icPayload`/`vidPayload`에 4개 이름 추가 (한 줄). 지침 수정으로는 불가능.
**이걸 안 고치면 [4-e] 전체와 versus·scale 관련 지침 항목이 공회전한다.**

## 4. 신규 발견 — 1차 진단서에 없던 것

### 4-1. 지침 내부 자기모순 — [4] 그래픽 애니메이션 예문 3/4가 [5-3] 금지 목록 위반 ★최우선

**[5-3] "영상에서 새로 그리게 하지 마라":**
> 가는 발광선, **와이어프레임**, 글자·숫자·라벨, …, **가는 스캔선**, …, 자가 작도되는 회로, 수천 개의 미세 입자

**[4] 그래픽 애니메이션 권장 예문:**

| 예문 | 판정 |
|---|---|
| ① `a hairline cyan arc gauge **draws itself** beside the structure and fills steadily…` | ❌ hairline(가는 선) + 자가 작도 |
| ② `a **thin cyan scan line** sweeps once…, a **faint wireframe** glowing briefly…` | ❌ 가는 스캔선 + 와이어프레임 — **둘 다 명시적 금지어** |
| ③ `a **fine cyan survey grid unfolds cell by cell** across the ground…` | ❌ 가는 선 자가 작도 |
| ④ `two slim cyan bars rise side by side…, then hold` | ○ 통과 |

[5-3]은 대체 문안까지 적어놨다 — *"가는 스캔선 → 넓고 부드러운 스캔 띠가 한 번 지나간다"*.
**자기가 금지하고 자기가 예문으로 권한다.**

**산출물이 그대로 받아썼다:**
- 컷 9: `a thin cyan scan line sweeps once across **the statue**, a faint wireframe glowing briefly where it passes, then fading` — 예문 ②에서 `structure`→`statue` 한 단어만 교체
- 컷 3: `a fine cyan survey grid unfolds cell by cell across the ground, following the terrain in perspective` — 예문 ③ **100% 동일**

→ 17컷 중 2컷이 720p에서 확정적으로 뭉개지게 되어 있다. 지침이 스스로 그렇다고 적은 것들이다.

### 4-2. 모델은 지침의 영문 예문을 **템플릿으로 소비**한다

```
[3-1]③ 예문 : the translucent cyan hologram of the conventional straight wall standing beside
              the real structure buckles and shatters into fading cyan fragments that dissolve
              in mid-air, while the real scene around it stays still and photoreal
컷 4 실제   : the translucent cyan hologram of the moai on log rollers buckles and shatters into
              fading cyan fragments that dissolve in mid-air, while the real scene around it
              stays still and photoreal
```

주어만 갈아끼웠다. 시사점 둘:

1. **예문 품질 = 출력 품질.** 규칙 문장을 다듬는 것보다 예문을 고치는 게 효과가 크다.
   (덧붙여 이 예문 자체가 [5-1] "인과 한 단계" 위반이다 — buckle→shatter→dissolve 3단계)
2. **편마다 같은 문장이 나온다.** "같은 결"은 의도지만 "같은 문장"은 다른 문제다.
   홀로그램을 쓰는 모든 영상이 동일한 붕괴 연출을 갖게 된다.
   → 예문을 2~3개 변형으로 주거나 *"예문을 그대로 쓰지 말고 이 문형으로 새로 써라"* 를 명시해야 한다.

### 4-3. 코드 안전망의 사각지대 — `GRAPHIC_MOTION_RE`

`strip_graphic_motion`(2322)은 강조 도구가 있는 컷에서 그래픽 절을 걷어내는 장치인데,
잡는 도형 목록이 다음뿐이다(2317):

```
bars? | lines? | arrows? | outlines? | overlays? | markers? | dots? | bands? | rings? | brackets?
```

**`grid`·`gauge`·`arc` 가 없다.** 즉 [4] 예문 ①(arc gauge)·③(survey grid)은 `anno_kind`가 있어도
안 걷힌다 → 두 벌 강조. 지침 예문 4개 중 **2개가 코드 사각지대**에 있다.
(산출물 컷 3은 `anno_kind=""` 라 지금은 무사하지만, `zone` 하나만 붙었어도 그리드와 영역선이 겹쳤다)

### 4-4. `shot` 필드가 카메라를 결정하는데, 지침이 그 사실을 안 알려준다

`_cam_for_cut`(6760~) 실제 우선순위:
```
1. anno_kind == "versus"                    → still (강제)
2. anno_kind 또는 focus_en 있음(quiet)       → wide/pov면 slowpush, 아니면 still
3. game 톤 + wide/pov                        → gamecam
4. CAMERA_AUTO_BEAT → CAMERA_AUTO_SHOT → CAMERA_AUTO_TYPE → "push"
   BEAT = {closing:pullup, solution:pushdown, pivot:push}
   SHOT = {wide:pullup, close:pushdown, macro:pushdown, pov:push, object:orbit, screen:push, cutaway:down}
```

**산출물 17컷 전수 대입 결과:**
```
 1 pullup     5 still      9 pushdown   13 still(versus 강제)
 2 slowpush   6 pullup    10 pushdown   14 pushdown
 3 pullup     7 push      11 pushdown   15 pushdown
 4 pullup     8 still     12 orbit(체인 전환)   16 pullup   17 pullup
```
**pullup 6 / pushdown 5 / still 3** — 카메라가 사실상 3종류. **9·10·11 이 3연속 pushdown**,
3·4 와 16·17 도 연속. 체인 컷(12)만 `CHAIN_TURN`(6881)으로 꺾인다 — **비체인 반복은 아무도 안 막는다.**

원인 둘 다 지침 쪽이다:
- **`shot` 이 wide/close 두 값만 쓰였다** (macro·pov·object·screen 0회). 지침은 shot을
  *"화각·배치만 정한다"* 고 설명하지만 실제로는 **카메라 워크 결정자**다.
- **`beat` 이 solution 에 7컷 몰렸다**(8,9,11,12,13,14,15 = 41%) → 전부 pushdown 으로 끌려간다.
  지침에 beat 분포 상한이 없다.

### 4-5. `weather_en` 충돌은 낮↔밤이 아니라 **과거↔현재**다

산출물에서 컷 11·12(과거, 상을 세우고 눈을 넣는 장면)와 컷 1·2·17(현재, 남아 있는 모아이)이
`"low sea wind with thin salt haze, warm dawn light across the grass"` **완전 동일**.
컷 15(수백 년 쓰러져 있는 상)도 컷 4·5·9(운반 중)와 동일 문구.
→ 규칙이 시킨 대로 한 결과 **수백 년의 시간 간격이 화면에서 지워졌다.**

### 4-6. 그 밖에 확인된 것

- **스키마 style enum 불일치**: [출력] 스키마는 14종만 나열하는데 [3] 본문은 `claysection`·`planline`
  을 지시한다. `norm_style`(1887)은 둘 다 받으므로 Opus가 쓴 컷 8은 정상 작동했으나,
  **enum만 보는 모델은 이 두 톤을 영원히 안 쓴다.** 폴백 경로에서 "치수·구조가 요점인 컷"이 전부 docu3d로 간다.
- **`type` 필드 사문화**: 6종 중 `product` 만 의미가 있다(뱃지·실물 전환·영상 기본 포함).
  나머지는 `CAMERA_AUTO_TYPE` 폴백용인데 그 앞의 `CAMERA_AUTO_SHOT` 이 7개 shot 값을 전부 덮고
  `shot` 은 항상 채워지므로 **도달 불가능한 분기**다(6773).
- **`evidence` × 홀로그램 충돌**: 컷 4는 `evidence="hypothetical"` + 홀로그램 컷.
  `EVIDENCE_LINES["hypothetical"]`(2750)은 *"복원부를 restrained luminous wireframe, 얇은 모서리와
  반투명 면으로"* 를 지시 — **홀로그램 지시와 같은 말**이 프롬프트에 두 번 들어간다.
  의미도 어긋난다: 컷 4의 홀로그램은 *기각될 가설*이고 evidence는 *이 컷 복원의 신뢰도* 축이다.
  [5-5]와 [3-1]의 상호작용 규칙이 지침에 없다.
- **캐논 55단어가 자세 지시를 묻을 위험**: 캐논이 자세 중립적으로 잘 짜였으나(서 있다/누웠다 없음),
  컷 5의 `lying face-down`·컷 15의 `toppled onto its side`가 **55단어 뒤**에 온다. 이미지 모델은
  앞쪽을 강하게 따르고 `SUBJECT_LOCK`(1891)이 "맨 위 SUBJECT를 그대로"를 한 번 더 강조한다.
  → 자세가 캐논과 다른 컷은 맨 앞에 상태 선언 권장: `toppled on its side: <캐논>, …`
  덧붙여 **컷 5와 15가 시각적으로 거의 같은 설정**(같은 길·쓰러진 상·docu3d·close·동일 weather)이라
  회수 컷이 재탕처럼 보일 위험이 있다.
- **톤 분배**: docu3d 11/17 = 65% ("절반 안팎" 상한 초과). 보조 톤 3연속 위반은 없음.
- **채널 철칙 누락**: 운영 철칙 *"solution 비트에 단면 또는 흐름 컷 1개 이상"* 이 지침에 한 줄도 없다.
  산출물이 이를 만족한 것(컷 8 claysection + full_section)은 규칙이 아니라 모델의 취향이다.

## 5. 확정 처방 — 우선순위

### 즉시 (지침 텍스트만, 토큰 증가 없음)

**① [4] 그래픽 애니메이션 예문 4개 교체** — [5-3] 준수형으로. 지금 확정 손실이 나는 유일한 항목.
   대체 방향: 가는 선·와이어프레임·자가작도 → **넓은 띠 / 이미 있는 것의 밝기 변화 / 굵은 경로 위 밝은 앞머리 하나**

**② 예문 재사용 금지 명시**
> 위 예문은 **문형 견본이지 복사용 문장이 아니다.** 대상·동작을 이 컷에 맞게 새로 써라.

**③ `shot` 의 실제 역할 명시**
> `shot` 은 화각이자 **카메라 워크의 근거**다 — wide는 물러남, close는 파고듦으로 풀린다.
> 같은 shot·같은 beat 가 3컷 연속이면 카메라도 3연속 같은 움직임이 된다.
> macro·pov·object 를 아껴 쓰지 말고 리듬이 필요한 자리에 써라.
> `beat` 은 한 종류가 전체의 1/3을 넘지 않게 — 특히 solution 이 몰리면 후반이 통째로 같은 카메라가 된다.

**④ 강조 배분 (1차 제안 3의 강화판)**
> 강조(`focus_en`)를 켤 컷은 **4개까지다. 넘기면 네가 고른 컷이 아니라 뒤쪽 컷부터 자동으로 꺼진다**
> — 후반의 회수 컷이 가장 먼저 죽는다. **뒤에서부터 예약하라**: `solution`·`pivot` 에서 반드시
> 살릴 컷 1~2개를 먼저 정하고 남은 자리를 앞쪽에 배분하라.
> **훅 컷의 강조는 `measure_en` 이 있거나 `anno_kind=glow` 일 때만 화면에 나온다.**

**⑤ `weather_en` 시점 축 (1차 질문 6의 답)**
> `weather_en` 은 장소가 아니라 **'장소 × 시점'** 단위로 묶는다. 같은 해안이라도 *지금 남아 있는
> 모습* 과 *과거 재현* 은 다른 대기다 — 같은 문구를 쓰면 수백 년의 간격이 화면에서 사라진다.
> 시점이 바뀌면 **한 축만 바꿔라**(빛 하나 또는 대기 하나). 전부 바꾸면 다른 장소가 된다.
> · 현재: `low sea wind with thin salt haze, cold flat daylight`
> · 과거 재현: `low sea wind with thin salt haze, warm low dawn light`

**⑥ `scene_ko` 규칙 신설 (지금 지침에 아예 없음)**
> `scene_ko` 는 **파일명이 된다 — 앞 12자만 남는다.** 12자 안에 '무엇이 찍혔는가'가 들어가야 한다.
> 피사체를 맨 앞에, 카메라·시간·수식은 뒤로. 15자 내외 명사구.
> 좋음: `모아이 얼굴 클로즈업` · `쓰러진 상 밑동` · `클레이 단면 D자 밑면`
> 나쁨: `새벽 해안 제단 위에 홀로 선 모아이를 올려다보는 저각 와이드`

**⑦ 기각 1회 규칙** (2장 문제 ③ 참조)
**⑧ 홀로그램 × evidence 배타** — 홀로그램 컷은 `evidence` 를 비운다
**⑨ 스키마 style enum 에 `claysection`·`planline` 추가**
**⑩ 채널 철칙 명문화** — solution 비트에 단면 또는 흐름 컷 1개 이상

### 지침 압축 (순증 상쇄용)

- `type` 6종 설명 → `product` / 그 외 2종으로 (도달 불가 분기)
- [3-1] 홀로그램 50줄 → 예시 4개 중 2개로 (한 영상 1~2컷짜리 연출이 지침의 11%를 씀)
- [4-d] 강조 도구 18종은 **줄이지 말 것** — 산출물이 실제로 쓴 4종의 선택이 전부 정확했다.
  문제는 개수가 아니라 **선택 순서가 없다는 것**. 맨 앞에 6줄 결정 트리를 얹고 18종은 참조표로:
  `반전/오해 → versus · 실패/금지 → reject · 여정 → flow|route · 방향 하나 → arrow ·`
  `수치 → measure · 크기 → scale · 빈 공간 → void · 나머지는 켜지 마라`

### 코드 (지침 범위 밖, 그러나 선행)

- `icPayload`/`vidPayload` 에 `from_en`·`to_en`·`compare_en`·`flow_of` 추가
- `GRAPHIC_MOTION_RE` 도형 목록에 `grid|gauge|arc` 추가
- (선택) `cap_anno_cuts` 의 동급 tie-break 를 `no` 오름차순 → **비트 가중치**로

### 보류 판정 — 1차 제안 1·2 (`plan` 블록 / 컷별 `검수_ko`)

**둘 다 채택 가치는 있으나 순위를 뒤로 미룬다.** 근거:
- `plan` 의 원 명분(캐논 표류 방지)이 반박됐다 → 남는 값어치는 검수 편의 + 폴백 내성
- 위 ①~⑩ 은 **토큰 증가 없이** 확정 손실을 막는다. `plan`+`검수_ko` 는 출력을 15~18% 늘린다
  (산출물 기준 약 6~7k → 8k 토큰, 회당 250원 기준 +40~45원)
- 도입 시 조건: `검수_ko` 는 **`scene_ko` 12자 규칙(⑥)과 세트일 때만** 의미가 있다.
  지금은 `scene_ko` 가 검수용 역할을 어중간하게 겸하며 파일명만 망치고 있다
- `cuts` 안의 역포인터(`캐논참조`)는 **비추천** — 캐논은 이미 지켜지고, 검증하려면 결국 사람이
  문구를 비교해야 한다. `plan` 안의 `등장컷: [1,2,5,7,9,11,12,15]` 배열이 한 줄 대조로 끝나 더 싸다

1. **4-1(예문 vs 금지목록 모순)의 대체 문안.** [5-3]을 지키면서 "한계·누적", "조사·분석",

3. **4-4(카메라 단조로움)를 지침으로 고칠 수 있는가.** `shot` 다양화를 지시하면

   적용하는 게 옳은가? (그건 범위 밖이지만 판단은 듣고 싶다)
4. **놓친 것이 더 있는가.** 특히 [5-1](인과 한 단계)·[5-2](분해뷰)·[5-4](reveal) 는
   이번 산출물에서 사용 빈도가 낮아 검증이 얕다.
